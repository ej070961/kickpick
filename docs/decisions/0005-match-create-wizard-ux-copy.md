# ADR 0005: 경기 생성 3단계 플로우와 문구 기준

## 상태

Proposed

## 날짜

2026-09-06

## 배경

현재 새 경기 생성 화면은 2단계 wizard로 구성되어 있다.

```txt
1. 경기 설정
   - 경기명, 날짜, 쿼터 수, 포메이션, GK 고정 여부
   - 등록 선수 선택 모달
   - 게스트 관리 모달

2. 쿼터 배정
   - 적은 쿼터 또는 많은 쿼터 배정 대상 선택
```

기능은 한 흐름 안에 들어와 있지만, 사용자가 가장 많이 확인해야 하는 참가 명단이 모달 안에 숨어 있다. 경기 조건과 참가 인원은 서로 영향을 주는데, 현재 구조에서는 사용자가 다음 내용을 한눈에 보기 어렵다.

- 선택한 포메이션에 필요한 최소 인원을 채웠는지
- 참가 명단에 GK가 포함되어 있는지
- 등록 선수와 게스트를 합쳐 총 몇 명이 뛰는지
- 출전 시간 조정 단계에서 어떤 선수가 계산 대상이 되는지

또한 “자동 배치 초안”, “쿼터 보정 대상” 같은 표현은 구현 관점에서는 정확하지만, 처음 쓰는 사용자에게는 다소 딱딱하게 느껴질 수 있다. KickPick은 경기 운영자가 빠르게 라인업을 준비하는 도구이므로 UI 문구도 실제 현장 언어에 가깝게 정리한다.

## 결정

새 경기 생성 화면은 3단계로 재구성한다.

```txt
1. 경기 정보
2. 참가 명단
3. 출전 조정
```

각 단계는 별도 큰 제목보다 설명, 상태 요약, 버튼 문구로 사용자의 다음 행동을 안내한다. 단계 표시에는 짧은 이름만 사용하고, 본문에는 과한 섹션 제목을 반복하지 않는다.

UI는 경기 전 준비 화면답게 차분하고 정돈된 운영 도구로 보이게 한다. 친근한 문구를 쓰더라도 시각 표현은 과하게 장식하지 않고, 사용자가 현재 단계와 필요한 선택을 빠르게 판단할 수 있게 만든다.

문구 톤은 다음 기준을 따른다.

1. 기능명보다 사용자가 하려는 일을 먼저 말한다.
2. “자동 배치 초안 생성”보다 “라인업 만들기”를 우선한다.
3. `참가 명단`, `라인업`, `출전`, `쿼터`, `포메이션`, `GK`처럼 경기 운영자가 실제로 쓰는 말을 사용한다.
4. 친근한 설명은 허용하되, 버튼과 오류 문구는 짧고 명확하게 쓴다.
5. 사용자의 선택을 강요하는 느낌보다 “정하면 만들어진다”, “필요하면 조정한다”는 흐름을 유지한다.

## UI 구성 기준

경기 생성 화면은 “정보 입력”, “명단 선택”, “최종 조정”을 순서대로 처리하는 작업 화면이다. 시각적으로는 밝고 명확하되, 카드와 색상을 많이 쌓아 난잡해 보이지 않게 한다.

### 텍스트 크기

- 페이지 설명과 단계 설명은 `text-sm` 또는 `text-base` 범위에서 유지한다.
- compact한 요약 카드, 선수 행, 검증 메시지에는 `text-xs`와 `text-sm`을 사용한다.
- 본문 안에서 hero처럼 큰 제목을 쓰지 않는다.
- 버튼 텍스트는 기존 shared button 흐름에 맞춰 `text-sm font-semibold`를 기본으로 한다.
- 숫자 요약은 강조가 필요할 때만 `text-base font-bold` 정도로 제한한다.

### 정렬과 밀도

- 같은 종류의 정보는 같은 축에 맞춘다. 예를 들어 참가자 요약의 label과 숫자 위치는 카드마다 동일해야 한다.
- 모바일에서는 한 줄에 하나의 주요 입력 또는 선택 그룹만 둔다.
- 데스크톱에서는 2열 구성을 사용할 수 있지만, 왼쪽은 주요 작업, 오른쪽은 요약/보조 작업으로 역할을 고정한다.
- 단계별 하단 액션은 sticky 영역에 두되, 버튼 개수를 최소화하고 주 행동이 가장 먼저 보이게 한다.
- 카드 안에 또 다른 카드가 반복적으로 들어가는 구조는 피한다. 목록, 요약, 폼은 구분선과 여백으로 구분한다.

### 컬러

- 기본 배경은 기존 `background`, `surface`, `card`, `border` 토큰을 따른다.
- `primary`는 현재 선택, 완료 가능 상태, 주 행동 버튼에만 사용한다.
- 오류와 주의는 기존 `mismatch` 계열과 옅은 배경을 사용하되, 한 화면에 여러 경고 박스가 동시에 떠 보이지 않게 우선순위를 정한다.
- 선택된 선수 행은 강한 배경색보다 얇은 좌측 강조선, 체크 상태, 은은한 surface 배경으로 표현한다.
- 단계 표시에서 완료/현재/대기 상태는 색상 하나에만 의존하지 않고 숫자, label, border 또는 weight 차이로 함께 구분한다.

### 사용성

- 참가자 수, GK 포함 여부, 최소 필요 인원은 사용자가 다음 단계로 가기 전에 항상 확인할 수 있어야 한다.
- 검색과 정렬은 선수 목록 바로 위에 붙이고, 결과 목록과 시각적으로 분리한다.
- 긴 선수 이름, 긴 포지션 표시, 작은 모바일 화면에서도 행 높이가 갑자기 흔들리지 않도록 한다.
- 선택 가능한 요소는 최소 `min-h-10`, 주요 버튼은 `min-h-11` 터치 영역을 유지한다.
- 사용자가 다음 단계로 갈 수 없는 이유는 버튼 주변 또는 현재 단계 요약 근처에 바로 보여준다.
- 3단계에서 조정이 필요 없는 경우 선택 목록을 억지로 보여주지 않고, 동일 출전 가능 상태를 먼저 보여준다.

## 3단계 플로우

### 1단계: 경기 정보

목표는 라인업을 만들기 위한 기본 조건을 먼저 정하는 것이다.

포함 항목:

- 경기명
- 경기 날짜
- 쿼터 수
- 포메이션
- GK 전 쿼터 고정 여부

권장 설명 문구:

```txt
날짜, 쿼터 수, 포메이션처럼 라인업을 짜는 데 필요한 기본 조건을 정해요.
```

필드 보조 문구:

```txt
경기명: 비워두면 날짜 기준으로 자동 저장돼요.
쿼터 수: 몇 번 나눠 뛸지 정해요.
포메이션: 이번 경기에서 사용할 기본 대형이에요.
GK 고정: 한 명의 골키퍼가 모든 쿼터를 맡을 때 켜주세요.
```

상태 문구:

```txt
{formation} 기준 최소 {slotCount}명이 필요해요.
```

다음 버튼:

```txt
다음
```

### 2단계: 참가 명단

목표는 이번 경기에 실제로 뛸 명단을 화면 본문에서 완성하는 것이다. 등록 선수 선택은 핵심 작업이므로 기본적으로 모달에 숨기지 않는다.

포함 항목:

- 등록 선수 검색
- 등록 선수 정렬 기준 선택
- 선수 참가 여부 토글
- 현재 목록 전체 선택 또는 해제
- 게스트 추가, 수정, 삭제
- 참가 인원 요약
- GK 포함 여부
- 포메이션 최소 인원 검증

권장 설명 문구:

```txt
등록 선수와 게스트를 함께 골라 이번 경기 명단을 완성해요.
```

요약 문구:

```txt
총 {count}명 참가 예정
등록 선수 {count}명
게스트 {count}명
GK 포함
```

검증 문구:

```txt
이 포메이션은 최소 {slotCount}명이 필요해요.
GK 고정을 사용하려면 참가 명단에 골키퍼가 있어야 해요.
```

다음 버튼:

```txt
다음
```

UI 구조:

- 모바일은 검색, 요약, 선수 목록, 게스트 관리를 세로 흐름으로 배치한다.
- 데스크톱은 선수 목록과 선택 요약/게스트 관리를 2열로 배치할 수 있다.
- 참가자 요약은 스크롤 중에도 확인하기 쉬운 위치에 둔다.
- GK 상태는 참가 명단에 골키퍼가 있거나, GK 고정 사용으로 인해 조치가 필요할 때만 간결하게 보여준다.
- 게스트 관리는 모달로 유지할 수 있지만, 추가된 게스트 목록과 삭제 액션은 2단계 본문에서 바로 보여준다.
- 단계 본문 섹션은 feature 전용 공통 프레임을 사용해 제목, 설명, 여백, 최소 높이를 맞춘다.

### 3단계: 출전 조정

목표는 인원이 쿼터별 슬롯에 딱 나누어떨어지지 않을 때만 출전 시간을 조정하는 것이다. 섹션 제목은 단계 표시와 같은 `출전 조정`을 사용하고, 본문에서는 계산 결과와 필요한 행동을 바로 보여준다.

포함 항목:

- 포메이션, 쿼터 수, 참가 인원 요약
- 모두 같은 쿼터 수로 뛸 수 있는지 여부
- 더 뛰거나 덜 뛸 선수 선택
- GK 고정 시 계산 제외 안내
- 생성 전 최종 요약

권장 설명 문구:

```txt
인원이 딱 나누어떨어지지 않을 때, 더 뛰거나 덜 뛸 선수를 정해요.
```

상황별 문구:

```txt
이번 경기는 모두 같은 쿼터 수로 뛸 수 있어요.
1쿼터 더 뛸 선수를 선택해주세요.
1쿼터 덜 뛸 선수를 선택해주세요.
고정 골키퍼는 출전 시간 계산에서 따로 처리돼요.
```

생성 버튼:

```txt
라인업 만들기
```

## 페이지 상단 문구

페이지 설명은 기능 나열보다 사용자가 얻는 결과를 먼저 말한다.

권장 문구:

```txt
경기 조건과 참가 명단을 정하고, 바로 수정 가능한 쿼터별 라인업을 만들어보세요.
```

조금 더 친근한 문맥이 필요한 위치에서는 다음 문구를 쓸 수 있다.

```txt
경기 조건과 참가 명단만 정하면, KickPick이 쿼터별 라인업을 먼저 짜드려요. 만들어진 배치는 경기장 화면에서 바로 수정할 수 있습니다.
```

## 문구 교체 기준

다음 표현은 사용자-facing 문구에서 줄인다.

```txt
자동 배치 초안 생성
쿼터 보정 대상
quota
selection
preset
```

대체 표현:

```txt
자동 배치 초안 생성 -> 라인업 만들기
쿼터 보정 대상 -> 더 뛸 선수 / 덜 뛸 선수
참가 선수 -> 참가 명단 또는 참가자
등록 선수 참가 여부 -> 이번 경기 참가 여부
```

내부 코드와 문서에서는 알고리즘 설명이 필요한 경우 `quota`, `보정`, `자동 배치`를 사용할 수 있다. 단, 버튼, 안내문, 오류 메시지에서는 사용자 행동에 가까운 표현을 우선한다.

## 구현 방향

권장 컴포넌트 구조:

```txt
MatchCreateForm
  -> MatchCreateStepNav
  -> MatchCreateHiddenFields
  -> MatchCreateStepGuard
  -> MatchCreateFooter
  -> match-info/MatchInfoStep
  -> participants/ParticipantsStep
       -> RosterPlayerPicker
       -> GuestPanel
       -> GuestFormDialog
  -> adjustment/AdjustmentStep
       -> AdjustmentSummary
       -> AdjustmentPlayerCard
```

`PlayerSelectionModal`은 핵심 선택 UI로 유지하지 않는다. 기존 검색, 정렬, 전체 선택, 체크박스 목록 로직은 `RosterPlayerPicker`로 옮겨 재사용한다.

경기 생성 상태는 저장 전 경기 초안을 의미하는 `MatchDraft`로 묶는다. 화면 컴포넌트는 값의 소유권보다 사용자 행동을 드러내는 action 이름을 사용한다.

```txt
MatchDraft
  -> info
  -> selectedRegisteredPlayerIds
  -> guestPlayers
  -> playtimeAdjustmentPlayerIds

MatchInfo
  -> name
  -> matchDate
  -> quarterCount
  -> formationKey
  -> gkFixed
```

권장 action 이름:

```txt
setInfo
toggleRegisteredPlayer
setSelectedRegisteredPlayers
addGuestPlayer
editGuestPlayer
removeGuestPlayer
setPlaytimeAdjustmentPlayers
resetPlaytimeAdjustment
```

`quota`, `reduced`, `roster`처럼 구현 또는 알고리즘 관점의 단어는 UI state와 컴포넌트 props에서 줄인다. 서버 액션 payload가 `reducedPlayerIds`를 요구하는 경우에는 제출 직전에만 변환한다.

파생값은 `MatchCreateForm`에서 직접 계산하지 않고 selector로 분리한다.

```txt
getMatchDraftSummary
getStepAccess
getDefaultPlaytimeAdjustmentPlayerIds
getReducedPlayerIdsForSubmit
```

단계 key는 숫자보다 의미 있는 문자열을 사용한다.

```txt
info
participants
adjustment
```

`MatchCreateForm`은 서버 액션 연결, 단계 렌더링, hidden input 제출만 맡긴다. 경기 조건이나 참가 명단이 바뀔 때 출전 조정 기본 선택값을 다시 계산하는 책임은 draft hook 또는 model 함수가 맡는다.

`GuestPanel`과 `GuestFormDialog`는 역할을 분리한다.

1. `GuestPanel`: 2단계 본문에서 추가된 게스트 목록, 추가/수정/삭제 버튼을 보여준다.
2. `GuestFormDialog`: 게스트 이름, 주 포지션, 부 포지션 입력만 담당한다. 모달 안에서 게스트 목록을 다시 보여주지 않는다.

새로고침 대응은 전역 상태관리 라이브러리보다 `useReducer + sessionStorage`를 우선한다. 경기 생성 초안은 `/matches/new` 화면 안에서만 의미가 있으므로 전역 store에 올리지 않는다. 저장 key는 버전을 포함해 추후 구조 변경 시 무효화할 수 있게 한다.

```txt
kickpick:match-create-draft:v1
```

## 구현 시 확인 사항

- 단계가 3개로 바뀌어도 서버 액션 제출 payload는 기존 구조를 유지한다.
- 1단계에서 경기 조건이 바뀌면 참가자와 출전 조정 계산이 다시 동기화되어야 한다.
- 2단계에서 참가자나 게스트가 바뀌면 3단계 기본 선택값을 다시 계산한다.
- `setupError`는 2단계의 참가자 검증 문구로 이동한다.
- 3단계에서 required count가 0이면 선수 선택 UI보다 “모두 같은 쿼터 수로 뛸 수 있어요.”를 먼저 보여준다.
- 모바일 sticky 하단 액션은 각 단계의 주 행동 하나가 먼저 보이도록 유지한다.
- 단계 표시 UI는 버튼으로 제공하고, 사용자가 미완료 단계로 이동하면 막힌 이유와 필요한 이전 단계를 안내한다.
- 새로고침 후 복구한 draft는 현재 등록 선수와 포메이션 목록을 기준으로 유효하지 않은 id와 formation key를 제거한다.

## 범위 제외

이번 설계는 새 경기 생성 화면의 UX와 문구 기준만 다룬다.

- 자동 배치 알고리즘 변경
- 경기 상세 편집기 구조 변경
- 선수 관리 화면의 우선순위 정책 변경
- DB 스키마 변경
- 경기 생성 이후 쿼터 순서 변경
